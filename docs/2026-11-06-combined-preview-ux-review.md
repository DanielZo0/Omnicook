# Combined preview UX review — 6 November 2026

Scope: browser walkthrough at a 443px viewport plus source inspection of social-preview/page.tsx, CombinedFlows.tsx and responsive styles. This is a review of the disposable combined preview, not an audit of deployed Omnicook. No product code changed. Existing real import/auth/AI/persistence capabilities must still be preserved during integration; mocked network actions are not counted as broken production features.

## Highest priority gaps

1. **Return context changes privacy labels.** Browser: Discover → A bowl of sunshine → Start cooking → Next step → Finish cooking. The completion dialog says the cooking photo is visible to a private family group, without selecting one. Closing it returns to a detail view labelled Private family recipe and Back to my cookbook. Source: cooking close/completion sets My cookbook regardless of origin; recipe privacy is inferred from the current screen. Keep source route, scroll/search and actual audience separately; finish privately, then optionally choose a destination. Cancelling the photo prompt should not imply a post.
2. **Sharing another cook’s public recipe is a dead end.** Browser: Discover → share A bowl of sunshine produces disabled destination checkboxes and Make my own version, with no copy/send link. Distinguish sharing an existing public link from publishing your own recipe. Family originals should only offer permitted member access, save/adapt; never broaden private access implicitly. Link creation/delivery remains intentionally mocked, but its UI journey must be represented.
3. **Unsaved work is discarded.** Browser: Add recipe → Write my own recipe → enter a title → Community → Add recipe. The entry flow restarts with no warning or recoverable draft. Preserve drafts and offer discard/continue when leaving. Recipe-edit dialog also closes on outside click/Escape without a dirty guard (source). Restore the original app's draft protection when integrating.
4. **Family activity is absent on mobile.** Browser: family activity right rail has no visible height at443px; CSS hides it at950px and below. Cooked activity and alternative updates have no mobile replacement. Put activity inline or behind Recipes / Activity within the selected cookbook; use a compact header instead of the large decorative banner.
5. **Cookbook management is incomplete.** Browser/source: membership dialog lists people, Remove, Invite. No pending invitations, revoke/resend, role changes, ownership handover, leave group, rename/archive or reported-content queue. Create cookbook requires Family → View our cookbooks → New cookbook. Add Create cookbook to the existing selector and a clearly labelled People & access/settings entry. Last-admin and member-removal outcomes need explicit UI states.
6. **Group identity does not scope all content yet.** Source: recipe destinations filter by group, but members/removals, activity and ingredient alternatives are global fixtures. Alternatives are matched by the word cream rather than selected group/recipe/ingredient. Switching cookbooks can show unrelated members/activity and suggestions. Model those contexts separately in the next preview; backend isolation remains future work. Newly created cookbooks need an honest empty state and first-invite/share actions.

## Redundancies and clarity

7. **Recipe action overload.** Source/browser: Share recipe at the detail heading and share on tiles, Start cooking/Add to meal plan, Saved, I cooked this, Make my own version and Edit. On mobile, several sit above the actual method. Keep Start cooking and Add to plan as the primary rail; one Save state and share icon; put edit/adapt/report secondary actions in a menu. Preserve owner control and attribution. Save on an owned recipe currently toggles it out of the Cookbook list; use an owned state instead, with explicit archive/delete if needed.
8. **Repeated Plan/Shopping controls.** Browser: bottom Plan and Shopping plus Weekly menu/Shopping list tabs, Back to weekly menu and planner shopping shortcut. Retain bottom shortcuts for the agreed five-action bar; remove redundant local switching/back controls where context is already clear. Preserve week and meal state. Browser adding orzo on Friday produced six quantity-aware shopping rows successfully.
9. **Unavailable nutrition dominates an empty plan.** Browser: each empty day repeats Unknown calories/protein/fibre and a note; nutrition setup/review is exposed despite lookup being unavailable. Collapse unavailable estimates/setup into one explanatory expandable section; keep meal selection and quantities prominent. Do not remove existing nutrition features. Current-week view shows today–Sunday, but generation still targets the full week; add an explicit remaining-days choice before changing that behaviour.
10. **Profile chrome repeats itself.** Browser: My feed and account avatar lead to own kitchen/profile; the page repeats Community title, kitchen banner, a one-item Published recipes tab, visitor explanation and private-cookbook shortcut. My feed remains the requested label; a short public-profile subtitle clarifies it. Replace the single-item tab with a heading, keep public recipes, and use the avatar for a real account/settings menu. Profile editing (photo/name/bio), following-list management and account/settings access are not represented fully.
11. **Owner visibility is hard to scan after the My feed change.** Source: My feed correctly shows only public recipes. Cookbook tiles show Your recipe or Shared with family, without listing all selected destinations. Restore destination chips or a concise status on owned Cookbook tiles, visible only to their owner. Do not expose cookbook names on public profiles. Keep the removed Manage sharing button removed; the existing share icon opens destination settings.
12. **Abuse and empty states need actionable outcomes.** Source: report suggestion uses the recipe-report dialog and can hide the whole recipe; blocking has no unblock/list management; photo/name/bio reporting is not represented. Scope reports to the selected object and audience, add block management and private admin/public moderator outcomes. Empty Following/search/cookbook states should give specific next steps; Explore recipes currently resets filters without always leaving an empty Family group. Keep public free-text comments absent. Cooking photos need per-recipe scope and an explicit audience rather than the current global photo fixture.

## Suggested next preview pass

1. Repair return context, draft protection and the public-link sharing path.
2. Complete compact Family header, inline mobile activity and People & access flow; scope fixtures to each cookbook.
3. Simplify recipe actions and planner/profile chrome; restore owner-only destination indicators in Cookbook.
4. Review profile/account settings, report/block flows, empty/error/loading/revoked-link states and kitchen/device acceptance.

No backend, deployment or code fixes were made during this review. A production preservation matrix already exists in docs/superpowers/specs/2026-11-01-social-integration-design.md; this review supplements it.

## Preview follow-through — 7 November 2026

The local preview now demonstrates the priority fixes and simplifications: draft retention/edit guard, return context and cooked-audience choice, public demo-link sharing, compact Family/mobile activity, group-scoped people/invites/settings/alternatives, owner destination chips, fewer recipe/planner/profile controls, account/profile/block management and targeted reports. See docs/social-preview.md for verification and boundaries.

Still pending beyond this pass: real production integration/persistence/access enforcement, notifications and invitation acceptance/revoked-link screens, real photo/profile-image lifecycle, arbitrary ingredient alternatives/revision handling, original app account settings integration, remaining-days generation and installed-device kitchen acceptance. The preview is not a replacement for existing Omnicook functionality.
